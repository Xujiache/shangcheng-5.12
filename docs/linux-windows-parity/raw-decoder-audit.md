# Windows RAW decoder and native engine audit

Scope: static inspection of the SHA-locked Windows 0.7.10 core archive and the pinned original source. The Windows executable was not run; no Windows RAW output comparison exists.

## Decoder identity and invocation

- [`ci-engines-v1.json`](../../vendor/flyingmouse-format/upstream-a7b9b15/ci-engines-v1.json#L6-L32) locks `ci-engines-v1-win32-core.tar.zst` to SHA-256 `d4f13034e719760790d75569b2dd9696facb88b15b8322f28d2aa4c3dbe6a835`. The verified archive member `dcraw/dcraw.exe` is 570,014 bytes, SHA-256 `865164a74162652bd29a729fae7918d8a7df60cf1b23a5dee182448ae0301c25`, and a Windows x86-64 PE executable.
- Its bytes contain `9.28\0` at offset 413291, immediately followed by `Raw photo decoder "dcraw" v%s` at 413297; `dcraw.c` occurs at 498826. The PE import table lists Windows runtime DLLs and `libjpeg-62.dll`, with no LibRaw DLL. This identifies the bundled program as Dave Coffin's **dcraw 9.28** by its embedded version/banner. Its exact compilation options and runtime behavior remain unverified.
- [Original RAW dispatch](../../vendor/flyingmouse-format/upstream-a7b9b15/image.js#L190-L216) copies the source to a temporary directory and invokes `DCRAW_PATH` as `-T -o 1 <input>` with a five-minute timeout. [`config.js`](../../vendor/flyingmouse-format/upstream-a7b9b15/config.js#L81-L90) resolves the packaged Windows executable. The Linux [Dockerfile](../../packages/server/Dockerfile.conversion-worker#L98-L107) builds `bin/dcraw_emu` from SHA-checked **LibRaw 0.21.5** source and [selects it](../../packages/server/Dockerfile.conversion-worker#L239-L251) through `FLYINGMOUSE_DCRAW_PATH`. The [Linux source patch](../../scripts/apply-flyingmouse-platform-fixes.cjs#L25-L47) retains `-T -o 1`; it adds a filename fallback and error handling. Same arguments do not establish identical camera support, demosaic, color, orientation, dimensions, or pixels between the two decoder families.
- The Windows binary's embedded help says `-6        Write 16-bit instead of 8-bit` at offset 415016 and `-T        Write TIFF instead of PPM` at 415104. LibRaw's `dcraw_emu.cpp` also assigns `output_bps = 16` only for `-6`/`-4`, while `-T` only assigns `output_tiff = 1`. Thus [`image.js`'s 16-bit TIFF comment](../../vendor/flyingmouse-format/upstream-a7b9b15/image.js#L190-L203) is inconsistent with the actual `-T -o 1` invocation. The expected default is 8-bit TIFF; this static audit does not substitute for reading the channel depth of actual Windows and Linux outputs.

## Other native engines

The original conversion source invokes LibreOffice, Poppler `pdftoppm`, FFmpeg, Pandoc, qpdf, the PDF layout docengine, and the advanced PDF structure engine in addition to dcraw. These are already tracked in [engine-audit.md](engine-audit.md); the candidate now [stages qpdf 12.4.0](../../packages/server/Dockerfile.conversion-worker#L193-L199) and [routes the original qpdf calls](../../packages/server/Dockerfile.conversion-worker#L239-L251) through that build. The pinned Pandoc path is set in the same environment block. The Windows archive also packages Poppler `pdfinfo.exe` and qpdf utility executables, but no direct invocation of those tools was found in the original conversion JavaScript. `avs3RM0Decoder.exe` is only assigned a path in [`runtime-paths.js`](../../vendor/flyingmouse-format/upstream-a7b9b15/runtime-paths.js#L16-L24) and an environment variable in [`electron-main.js`](../../vendor/flyingmouse-format/upstream-a7b9b15/electron-main.js#L199-L209); no direct conversion call was found. This static source inventory establishes no additional missing standalone conversion engine. It does not prove equivalence of native libraries inside the packaged applications or npm modules.

Reproduce the Windows string evidence from the cached private archive member with `shasum -a 256 dcraw.exe`, `strings -a -t x dcraw.exe`, and `objdump -p dcraw.exe`. Archive and selected member are retained under `/Users/mac/Library/Caches/ledger-flyingmouse-engines/windows-core-audit/`; no original binary is committed.
