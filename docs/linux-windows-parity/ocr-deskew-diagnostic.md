# OCR deskew diagnostic

Two synthetic PNGs are frozen under [`fixtures/ocr`](fixtures/ocr). `false-deskew.png` is the exact 600×320 image generated by the image branch of `verify-local-original-conversion.cjs` on the Linux candidate, with Noto Sans CJK SC, visible text `量窗助手 12345`, and the green rectangle. SHA256: `67d1c1113635641cc8f327bf0029320be13a85a56e5f602465e37983a3c9bfa1`. `invoice-skew5.png` is a 1256×802 synthetic 5° skewed invoice with visible title `采购明细单`, body `门窗订单` and `安装费用`, and amounts `474.00`, `712.00`, `1186.00`. SHA256: `fbd86c070b3fcc1a293a917808713669891ee6388c17213eabe5f292ee19e3c8`. Both contain only synthetic data. The checked-in bytes, rather than a font-dependent regeneration, are the replay inputs.

Run the [candidate audit](../../scripts/audit-flyingmouse-ocr-deskew.cjs) with the runtime containing the original `ocr.js` and the staged `eng+chi_sim` models. The tested Linux image has a separate maximum-pixel preprocessing guard in `ocr.js`; for an untouched source comparison, bind-mount the pinned file (SHA256 `1ddc8b79a9ec6db76677d5905c1d8e0a6a99ef1afe6a553ec7f1319e73302636`) over that one runtime file. From the repository checkout on the Linux host:

```sh
docker run --rm --network none --memory 2g --cpus 2 \
  -v "$PWD":/audit:ro \
  -v "$PWD/vendor/flyingmouse-format/upstream-a7b9b15/ocr.js":/app/flyingmouse/ocr.js:ro \
  --entrypoint node jiujiu-conversion-worker:linux-parity-f362437 \
  /audit/scripts/audit-flyingmouse-ocr-deskew.cjs /app/flyingmouse > /tmp/ocr-audit.json
# Add --rotations after /app/flyingmouse to generate 90° and 180° physical rotations.
```

The script verifies both input hashes, runs Tesseract PSM 6 with `rotateAuto:false` and `true` on the *same prepared pixels*, records text/confidence/deskew angle/line baseline, then runs the original public `recognizeImageResultWithWorker` route. Exit status is **1** whenever the original result omits any visible expected phrase. This is a deliberately red fidelity gate on the current Linux original OCR path, not a passing repair test. The isolated run against candidate image `jiujiu-conversion-worker:linux-parity-f362437` produced `untouched-candidate-audit.json` under `e2e/artifacts/image-ocr-diagnostic` and exited 1. Its JSON was byte-identical to the image's maximum-pixel-guarded OCR runtime for these inputs:

| Input | No automatic deskew | Automatic deskew and original route | Missing visible text |
| --- | --- | --- | --- |
| Upright | `量窗助手 12345`, confidence 80 | `星窗助手 12345`, confidence 89, estimated 1.05° | `量窗助手` |
| 5° skew | `米购明细音`; `门窗订单`, confidence 86 | `采购明细单`; `| ]窗订单`, confidence 84, estimated −4.20° | `门窗订单` |

For the upright image, physical 90° and 180° rotations followed by orientation correction gave the correct phrase without automatic deskew (confidence 73 and 67); automatic deskew again corrupted it (confidence 88 and 61). The original route returned `星窗助手 12345` for 90° and `OCR_LOW_CONFIDENCE` for 180°. The four-case audit is retained as `stock-candidate-rotations-audit.json`; it exits 1. On the skewed invoice, no-deskew line baselines remain 1.85–3.72° from horizontal; automatic deskew reduces them to 0.08–0.67° while damaging one body line. Therefore neither the existing page-level confidence nor the flatter whole-page baseline identifies a lossless result across these samples. The trial policy that skipped deskew after any `reliableOcr` result was reverted: the skewed no-deskew candidate is reliable by that check yet has a damaged title. No new OCR algorithm has been accepted.

The untouched pinned source tests `ocr-quality.test.js`, `pdf-ocr-regions.test.js`, and `ocr-page-diagnostics.test.js` pass **14/14**, with **4 actual-model tests skipped** unless separately supplied audit samples are present. Their replay worker checks original call order (`rotateAuto:true` first), so those tests would conflict with a no-deskew-first policy; do not edit them to manufacture a green result. The image pair validator correctly fails the missing Chinese glyph.

Windows has **not** run these exact PNG bytes through its original engine. The JavaScript `ocr.js` is common source, but Tesseract core, Sharp/libvips, prepared raster and model loading are runtime inputs. A Windows failure on the same frozen bytes would establish an original cross-platform behavior defect; a Windows success would point to a platform/runtime difference to isolate with the audit's prepared raster, model and core hashes. Neither outcome is established by this Linux run.
