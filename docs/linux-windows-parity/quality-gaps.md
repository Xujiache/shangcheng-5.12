# Conversion parity quality gaps

Audit basis: pinned original `a7b9b15`, tracked synthetic fixtures, and the candidate integration as of 2026-09-29. No Windows reference artifact was produced: the GitHub Actions account billing lock prevented the Windows job from starting. A Linux conversion result or matching engine version is not a Windows output comparison.

## Windows reference workflow scope

[`conversion-windows-reference.yml`](../../.github/workflows/conversion-windows-reference.yml) has the necessary *declared* Windows engine setup: Node 24, `npm ci`, Pandoc restoration, both SHA-locked Windows engine archives, and paths to FFmpeg, LibreOffice, Poppler, Tesseract data, docengine and docstructure. The restore script checks archive hashes and the docstructure lock before use. If that job can run and all dependencies are available, [`flyingmouse-platform-reference.cjs`](../../scripts/flyingmouse-platform-reference.cjs) can produce direct original CLI evidence for the **six** tracked cases: native, scanned and mixed PDF, each to DOCX and XLSX. It checks source hashes, text phrases, DOCX media count and layout fallback warnings; it stores converted files, environment details, page raster hashes and dimensions. This is a runnable design, not execution evidence. Its artifacts expire after 14 days, so retain any successful reference outside Actions before expiry.

The workflow does not generate reference outputs for the other 1,168 catalog pairs, RAW, legacy Office/OFD/WPD, standalone image OCR, protected PDF options, or non-PDF media. [`matrix-fixtures.json`](matrix-fixtures.json) lists public and native synthetic candidates; they require additional Windows reference runs using the exact same bytes and output options. Historical `954/1174` acceptance remains separate from Linux parity.

There is also a deterministic blocker in the existing six-case gate. On the tracked `native-table.pdf`, direct original `classifyPdf` reports `native`, 95 text characters and image coverage `0.02874308868440488`; `extractPdfRowsByPage` reports the same nonzero coverage. [`pdfPageNeedsOcr`](../../vendor/flyingmouse-format/upstream-a7b9b15/pdf.js#L99-L103) treats **any** nonzero image coverage as needing OCR, and [`convertPdfToDocx`](../../vendor/flyingmouse-format/upstream-a7b9b15/pdf.js#L797-L813) rejects an otherwise complete docengine result when `source.some(pdfPageNeedsOcr)` is true. It falls through to the simplified DOCX path, which emits `PDF_DOCX_LAYOUT_FALLBACK` if it completes ([return](../../vendor/flyingmouse-format/upstream-a7b9b15/pdf.js#L872-L888)); the reference runner marks that warning failed. The small illustrative bitmap in the native fixture is enough to trigger this path. This is original source behavior on both OSes; restoring Windows Actions alone cannot make that case pass. Separate a *full-page scan needing OCR* from a native page with a small figure using the existing page coverage/classification evidence, then rerun native→DOCX on both platforms. Do not waive the warning as a substitute for preserving layout.

Candidate platform fix revision 17 in [`apply-flyingmouse-platform-fixes.cjs`](../../scripts/apply-flyingmouse-platform-fixes.cjs) changes only the runtime copy: the original `pdfPageNeedsOcr` remains intact for text OCR, while a separate `pdfPageNeedsLayoutOcr` reuses original `classifyPageMetrics` only when accepting a DOCX layout result. Revision 16 changed the predicate globally and regressed the original partial-scan text tests; it is superseded. [`test-flyingmouse-pdf-ocr-routing.cjs`](../../scripts/test-flyingmouse-pdf-ocr-routing.cjs) passes 4/4 against a fresh revision 17 runtime, including native text above a partial scan still receiving OCR. The complete original `pdf-ocr-regions.test.js` and `pdf-page-completeness.test.js` files also pass (17 pass, 2 environment/model skips). The native focused test fails against the untouched pinned source with `PDF_OCR_REQUIRED`, proving the original/candidate difference. DOCX layout acceptance can retain a small scanned body as an image beneath native text without making that image's text editable; this boundary still needs real output-quality checks. Windows original reference for this case remains unrun and cannot be labeled passed.

## Concrete risks and required comparisons

| Area | Evidence and risk | Smallest useful acceptance check |
| --- | --- | --- |
| PDF DOCX layout | The original `pdf.js` first runs `docengine convert`, validates editable text coverage, and may route failure to docstructure or a simpler PDF.js reconstruction ([route](../../vendor/flyingmouse-format/upstream-a7b9b15/pdf.js#L796-L845)). The Linux candidate restores the Windows entry and patched `pdf2docx` modules; the [isolated probe](exact-docengine-probe.md) proves import and native output, not Windows page geometry. | Same native PDF on Windows and Linux: inspect DOCX paragraph/table/media structure, render both with each platform's LibreOffice, compare page count and visible placement. Include formula-heavy and multi-page header/footer inputs beyond the one-page fixture. Fail on `PDF_DOCX_LAYOUT_FALLBACK`. |
| Scanned and mixed PDF | The [isolated structure probe](scan-machinebrief.json) extracted a real 3×2 editable table from the tracked scan with 37 model files and a sampled memory peak above 4 GiB. The model pipeline and renderer are usable, but no Windows visual reference exists. `pdf-classifier.js` intentionally treats documents with fewer than 20% scanned pages as native; that boundary can leave a minority scanned page as an image in layout conversion ([classifier](../../vendor/flyingmouse-format/upstream-a7b9b15/pdf-classifier.js#L29-L54)). This is an original behavior boundary, not a Linux-only regression. | Compare all six PDF reference cases, including table cell order, OCR confidence/warnings, image positions and rendered pages. Add a six-page fixture with one scanned page for the original classifier boundary; record the expected behavior explicitly. |
| Reference checker blind spots | The Windows direct checker and Linux direct/backend checker share [source-aware assertions](../../scripts/flyingmouse-pdf-parity-quality.cjs): all declared DOCX phrases must appear once per source page, the native fixture requires one rendered DOCX page, and XLSX must contain the known three-row, two-column table once per source page. The original structured PDF writer intentionally adds an `Original reference` section with one source-page image per PDF page, so scan/mixed total DOCX pages cannot be equated with source pages. Both checkers invoke the original structured DOCX validator for heading, ordered image markers and package relationships; Linux also compares embedded reference RGB pixels exactly with the source PDF rendered by the original PyMuPDF 2× rule. Linux compares direct/backend text and rendered raw pixels without artifact-path false mismatches. These checks do not yet assert DOCX table geometry, merged cells, formula layout, or exact page-by-page placement of editable content. The native fixture produced three pages in Linux and Mac LibreOffice; Word/WPS behavior and the untouched Windows baseline remain unrun. | Inspect retained DOCX/XLSX structures and rendered pages against each source. Keep a passing row scoped to its known phrases/table cells and fixed-fixture page assertions until visual comparison and a Windows reference exist. |
| Fonts and rasterization | The original Windows archive does not bundle Noto CJK TTF; Windows font selection is an environment input. Linux stages Noto Sans CJK and a dedicated Fontconfig/Poppler stack ([audit](engine-audit.md#L16-L22)). Equivalent LibreOffice and Poppler release numbers do not guarantee equivalent font substitution or glyph metrics. | Record `fc-match`/effective Linux font and the Windows substitution for Chinese, Latin and formula glyphs. Compare render page dimensions and overlays, then inspect differences visually; raw pixel hash mismatch alone is not a failed semantic conversion. |
| RAW | Original `image.js` invokes bundled `dcraw.exe` with `-T -o 1`, producing a 16-bit sRGB TIFF ([route](../../vendor/flyingmouse-format/upstream-a7b9b15/image.js#L190-L216)). Linux invokes LibRaw 0.21.5 `dcraw_emu` through the same flags ([audit](engine-audit.md#L15)). Those programs can differ in sensor support, demosaic, orientation, white balance or pixel values even when both decode. Public RAW samples currently establish input authenticity and Linux decode only. | On Windows, run the exact cached public RAW hashes through bundled `dcraw.exe`; compare decoded TIFF dimensions, orientation, channel depth and representative color/pixel statistics with Linux. Then compare final requested targets. |
| Office input/output | Windows uses LibreOffice 26.2.1.2 and Linux stages the same release number, but native libraries and fonts differ. The six WPS-family samples in [`matrix-fixtures.json`](matrix-fixtures.json) were genuinely saved by WPS Office; WPD and OFD public originals include two inputs whose hashes match historical accepted files. None is in the six-case Windows workflow. | Run identical WPS/WPT/WPD, ET/ETT, DPS/DPT and OFD inputs through Windows and Linux original CLIs. Check Chinese, spreadsheet formulas/results, slide count, embedded images, table geometry and rendered page count; record engine warnings. Keep private historical samples out of shared artifacts. |
| OCR | Original JS OCR uses `tesseract.js` with `eng+chi_sim`, `cacheMethod:none`, `preserve_interword_spaces=1`, and `user_defined_dpi=300` ([worker](../../vendor/flyingmouse-format/upstream-a7b9b15/ocr.js#L95-L116)). The separate `tesseract-ocr` CLI is not that path. The same traineddata bytes do not by themselves prove equal preprocessing: PDF rendering and Sharp/libvips affect pixels fed to OCR. | Compare source raster SHA/dimensions before OCR, traineddata/core hashes, recognized words, bounding boxes and confidence on identical image and PDF fixtures. Preserve exact numerals and punctuation. |
| Resource envelope | Original docstructure preflight requires at least 5 GiB free memory and runs under a ten-minute timeout ([source](../../vendor/flyingmouse-format/upstream-a7b9b15/pdf-structure-engine.js#L16-L33)). Do not infer a 4 GiB production container is sufficient. |

The retained Linux native DOCX renders as three LibreOffice pages from one PDF page, with right-column text, table and figure split across later pages. Direct and backend DOCX have identical document XML. The restored original `pdf2docx` modules and public 0.5.8 both render this fixture as three pages; increasing `min_section_height` from 20 to 80 reduces it to two but leaves the legend alone on page two. Replacing `nextColumn` with `continuous` and adding a column break gives one page while placing the legend about 49 pt below its source position. These are diagnostic copies, not accepted layout repairs. The [column diagnostic](pdf-column-diagnostic.md) records a one-page table-cell candidate that regresses a tall one-page source to three pages; no runtime patch was accepted. Word/WPS and the untouched Windows baseline have not been rendered; the native one-page gate remains failed.

The separate Chinese long-line PDF in `run-20260928T210236Z-464959/pdfContent-inputs` exposed a real glyph loss in the restored Windows-patched `RawPage.calculate_margin`: it inferred a 72 pt right margin and clipped the terminal `数` and `这` glyphs before DOCX creation. The Linux [wrapper](../../packages/server/scripts/run-original-docengine.py) now bounds inferred margins by cleaned visible block and shape extents while retaining the hash-locked entry and modules. The [real-engine regression](../../scripts/test-original-docengine-visible-margins.py) confirms exact 150-character normalized source text in the repaired one-page DOCX, and byte-identical document XML to the original algorithm for the tracked native table/image fixture and a blank PDF. Isolated evidence is saved as `pdf-content-diagnostic/margin-review.json`; Windows conversion output remains unmeasured, so this is an explicit runtime behavior repair, not a claim of Windows result parity.

The frozen PNG in `run-20260928T212000Z-529239/image-inputs` visibly reads `量窗助手 12345`, but the original image→DOCX path produced `星窗助手 12345` after Tesseract's automatic deskew estimated about 1.05°. On the same prepared pixels, disabling automatic deskew recognized the visible phrase; the false deskew persisted when the source was physically rotated and then corrected. A trial policy that skipped deskew whenever the first OCR result met the existing reliability check was rejected: on a real 5° synthetic invoice, the uncorrected result met that check while corrupting `采购明细单`, and automatic deskew fixed the title but corrupted a different body line. Page confidence alone and whole-page baseline slope therefore cannot choose a lossless candidate for both inputs. No OCR policy patch has been accepted, and the untouched Windows output for these bytes has not been measured. The [replay diagnostic](ocr-deskew-diagnostic.md) records the two frozen inputs, runnable red fidelity gate, candidate texts and Linux evidence. The original OCR tests pass 14 with 4 actual-model skips on pinned source.

Before changing the acceptance ledger, retain the Windows `reference.json`, `environment.json`, source/output hashes and output/render artifacts; compare them with Linux direct-engine and authenticated backend evidence for the same input and target. Record each pair separately, including failures and warnings.
